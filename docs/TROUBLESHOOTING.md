# Troubleshooting

**Start here:**
- On the phone (Termux): `curl -s http://127.0.0.1:8121/health` should print `ok`. `curl -s "http://127.0.0.1:8121/health?ytdlp=1"` adds yt-dlp health (`ok`, `ver`, `heal`, `heal_ts`).
- `tail -50 ~/music-stream/server.log`
- `tail ~/music-stream/run.log` (start/exit lines)
- `tail ~/music-stream/ms-update.log` (yt-dlp updates)
- `tail ~/cf/tunnel.log`
- In the app: Settings → **Diagnostics** shows the service-worker state, build, the last play events and the reason for any error.

| Symptom | Likely cause | Fix |
|---|---|---|
| **Site shows Cloudflare 502 / 530 / 1033** | Android closed Termux, or cloudflared died | Open Termux and run `bash ~/wd.sh`, then wait 1 min. From the desktop: `C:\Users\<you>\recover_phone.ps1` (adb wakes the phone and types the command). Make sure Termux's battery setting is Unrestricted and the wakelock is held. Check that **no second phone** runs `my-music-tunnel`. |
| **Site down and ssh to :8022 refused** | **Termux killed** (it happened on 10 Nov when a heavy test used up the memory) | As above. Never run test suites on the phone. After a reboot, Termux:Boot starts everything within about 2 min, once the phone has been unlocked. |
| **"Sign in to confirm you're not a bot" in server.log / songs fail in bursts** | YouTube **bot-check** on the phone's IP. It's IP-wide, not tied to one client | The server already backs off: background lookups pause for 2 min after a bot-check (`_bg_blocked`), the CLI fallback is skipped, and visionos isn't blamed. Wait it out, and avoid bulk prefetch or downloads. **Don't add YouTube cookies.** That's the owner's decision only (account risk). |
| **Log shows `xt visionos failing -> default clients for 30 min`** | **Client switching**: the visionos player client stopped working | Expected self-healing: the default clients are used for 30 min. Per-video failures are remembered in `_KBAD`. If both kinds fail, update yt-dlp (UPDATES.md) and check that `node` and yt-dlp-ejs are installed. |
| **Loading circle spins forever / Next keeps looping without playing** ("circles loop") | The radio refill was rate-limited (429) during fast skipping, or the next item can't be resolved | Since v69, `/api/radio` has its own rate bucket. The stall watchdog (12 s) tries another format, then retries or skips. Check Diagnostics for `play-stall` / `start-stall`, and `server.log` for 429 or bot-check. Reload the app if a tab has been open since before an update. |
| **Song sticks at 0:00 or stops mid-song** ("songs sticking") | The upstream URL expired, a chunk fetch stalled, or it's a live/upcoming stream | The player cycles formats after 12 s, then retries or skips. Live/upcoming videos return **409** (`X-MS-Unsupported: live`) and can't be played; past-stream recordings work. Check `/health?ytdlp=1`. If `heal` says "extractor still broken", update yt-dlp (it did on 11 Nov 10:00 IST). |
| **Video only offers AV1 or doesn't start; audio fine** | The **yt-dlp-ejs** challenge solver or the JS runtime is missing, so only some renditions unlock; AV1 doesn't decode on many devices | `python -m pip install -U "yt-dlp[default]"` (pulls yt-dlp-ejs), `pkg install nodejs`, and `YTDLP_JS_RUNTIME=node` in music.env. The server prefers **H.264/avc1** mp4 (`c=h`) and uses AV1 only when asked (`c=av1`). `/api/vinfo?id=` shows the real heights. |
| **Search is slow (several seconds)** | The first query after a restart is cold, or the fast path failed and fell back to yt-dlp | `server.log` shows `search fast ms=…` (fast path) or `search fast fail … -> yt-dlp`. `SEARCH_FAST` must not be 0. The disk cache (`lcache/search`, 6 h) makes repeat queries instant. A cold yt-dlp fallback takes 2–4 s on the phone. |
| **"Too many attempts" at sign-in** (lockout) | 10 wrong passwords for that name from that place within 15 min (or 30 per IP or /64, or per user, from outside) | Wait 15 min, or sign in at home (an admin is never locked from the phone or the home Wi-Fi), or unlock: `ms-recover` in Termux, the "Unlock Music Stream" widget, `http://127.0.0.1:8121/recover` in the phone's browser, or `ms-recover.cmd` on the desktop copy. |
| **`/recover` says forbidden** | Opened through the tunnel, Funnel or another device | It only works on the server device itself (loopback, no proxy headers). |
| **Everyone signed out / settings jump around** | **Two machines running the same tunnel** | Stop one (NEW_PHONE_SETUP.md, section 4, step 4). |
| **"… was running under 20 fps … switched to Neon Bars" (was "Smoother mode for this device")** | The Dancer / Club Stage / Cinematic 3D scene stayed slow. Since 2026-11-11 the first 5 s after a model, theme or tab-return are not measured, hidden time is ignored, and quality steps down first (shadows off → lower pixel ratio → fewer particles); it falls back only after ~8 s under 20 fps at the lowest level. Before that, one slow second (often the first after unlocking the phone) was enough | Tap **Keep 3D** in the notice: this turns the auto switch off for that user (`vizKeep3D`, synced). The switch is never remembered: the next app open starts in the chosen mode. Remove `vizKeep3D` from localStorage to turn the auto switch back on. |
| **18+ dance/visuals missing (404)** | Expected unless the signed-in user has the 18+ flag | An admin turns it on per user in the users page. It's never cached and always `no-store`. |
| **mp3 download fails** | No ffmpeg | Install ffmpeg, or use the original-format download (m4a/webm is served automatically without ffmpeg). |
| **Phone unreachable from the home Wi-Fi (Android 15 or newer)** | Local-network permission | Allow Termux "Nearby devices / Local network", or `adb shell pm grant com.termux android.permission.ACCESS_LOCAL_NETWORK`. |
| **App still shows old behaviour after an update** | The tab was open before the update; there's no auto-reload | Close and reopen the app, or pull to refresh. Diagnostics shows the service-worker build (`ms-vNN`). |
| **Lyrics missing or wrong language** | Not on lrclib, or the karaoke provider timed out (12 s) | Expected; try the manual search in the lyrics panel. Translation uses Google's public endpoint and may be rate-limited. |
| **Desktop 8121 slow to come back after a restart** | `run.ps1` runs a pip upgrade before every start | Wait 10–30 s. Make sure you stopped the 8121 pid, never 11888 (the 8120 service). |
